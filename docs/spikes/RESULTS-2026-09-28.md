## E1 details: what is left to build (our code, not a fork)

arti on `wasm32` needs a **runtime** that implements `tor_rtcompat::Runtime`:

| Trait | Our implementation |
|---|---|
| `Spawn` | `wasm_bindgen_futures::spawn_local` (single thread; arti's futures are `Send`, which is harmless here) |
| `SleepProvider`, `CoarseTimeProvider` | `setTimeout`-based timers; `coarsetime` already uses `performance.now()` |
| `Blocking` | Run inline. There are no threads (Pages cannot enable `SharedArrayBuffer`) |
| `NetStreamProvider` (TCP) | Returns "unsupported". **All** channels go through bridges, via our PT manager |
| `UdpProvider` | Returns "unsupported" |
| `TlsProvider` | arti's `rustls` impl with the **ring** provider installed at start-up |
| PT manager (`AbstractPtMgr`) | **Snowflake in Rust:** broker `fetch` → `RTCPeerConnection` to the proxy (web-sys) → encapsulation → KCP → smux → a byte stream handed to arti as the bridge channel |

- **Caveat:** browser objects such as `RTCDataChannel` are `!Send`. The Snowflake transport runs in a local task and talks to arti through `Send` channels (`futures::channel::mpsc`). This is a known pattern, but it has to be designed carefully.
- **State and directory cache:** arti uses an in-memory state manager on wasm. Persisting guards and the consensus cache to IndexedDB is our addition, needed for a fast warm start (gate G3).
- **Not yet measured:** the size of the final Tor WASM module and bootstrap time (E4/E6), because both need the runtime shim first.
