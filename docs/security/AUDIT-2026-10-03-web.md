## Findings

### W-1 (high): A new build runs without the user's consent

**What is promised.** §17.1 says a new `sw.js` installs and waits, and "activates only on user
consent". §5 and §21 list "a service worker that pins the version and asks before updating" as
the mitigation against a static host that serves altered code. §17.2 calls `index.html` "the root
of trust, pinned by the service worker".

**What the code does.**

- `app/sw.js:16-25`: install precaches the new files; activate deletes every other cache.
- `app/sw.js:40-43`: `skipWaiting` runs only when the page posts `'activate'`.
- `app/app.js:1794-1821`: the page offers the update and calls `reg.update()` on every
  `visibilitychange`.

Nothing prevents two cases:

1. **An honest build activates when the app is closed.** Under the Service Worker lifecycle, a
   waiting worker becomes active once no client uses the old one. The user closes the tab or
   swipes the PWA away, reopens it, and the new build runs without the prompt ever being
   answered. Phone users close the PWA all the time.
2. **A hostile host does not wait at all.** The browser fetches `sw.js` from the network and
   runs the new script's own `install` handler. A hostile `sw.js` calls `self.skipWaiting()` and
   `clients.claim()`, and the next load runs the attacker's page. The app itself triggers the
   update check every time the tab comes to the foreground (`app/app.js:1820`). Shift+Reload also
   bypasses the SW.

**Reproduction** (`sw_proofs.mjs`, P1 and P2):

```
p1_v1_title: "Ephem"
(host serves a new sw.js + index.html; reg.update(); worker waiting; banner shown, never tapped)
p1_still_v1_while_open: "Ephem"
(page closed, new page opened)
p1_after_reopen_title: "Ephem V2 (not consented)"      p1_after_reopen_sw_version: "v2-test"
p2_title_after_reload: "hostile build"   (hostile sw.js with skipWaiting, tab never closed)
```

**Impact.** For an honest update, the consent step is cosmetic. Against the attacker it exists
for (the host, or a compromised GitHub account or Pages deploy), the "pinning" gives no
protection: that attacker's code runs in every returning user's tab on their next visit. It can
read keys, contacts and messages and break Tor anonymity. The documents present this as a
mitigation. P9 requires the UI and docs to state the trust in the static host honestly.

**Fix.**

- *Honest updates:* make the consented version an explicit pointer that the worker honours.
  - The new worker precaches into `ephem-<new>`, but its fetch handler serves from the cache
    named by `accepted` (one key in a tiny IndexedDB store, or a `Cache` entry) until the page
    sends `'activate'`. The page then sets `accepted = <new>`, and the old cache is deleted only
    after that.
  - Closing the app no longer switches versions.
- *Hostile host:* this cannot be fixed inside the web platform. Say so in §5, §17 and §21, and on
  About ("a changed `sw.js` from the host runs on your next visit").
- Offer out-of-band verification:
  - the build id compared with the signed release hash (already planned), with steps to follow;
  - optionally, a content-addressed entry (an IPFS CID gateway URL) for users who want one.

### W-2 (high): Every page on `<owner>.github.io` shares Ephem's origin

**Evidence.**

- The deployment is a GitHub Pages *project* site, `https://darkcite.github.io/ephem/` (README
  line 13; P2P-CHAT.md header table). Its origin is `https://darkcite.github.io`, shared by every
  other Pages site of the `darkcite` account. It is also shared by everything in this repo's
  deployed tree, which is the repo root with `.nojekyll`.
  - That tree includes test pages with inline scripts and no CSP: `checks/web/index.html`,
    `checks/tor-lab/web/index.html`, `checks/spikes/equix_bench/bench.html`.
- Origin-scoped state that Ephem trusts:
  - Cache Storage `ephem-<build>`: the pinned app (`app/sw.js:13,30-37`);
  - IndexedDB `ephem/slots`: encrypted key files with plaintext label and handle
    (`app/slots.js:9-18`);
  - IndexedDB `ephem-tor`, `ephem-channels`, OPFS, localStorage;
  - the service-worker registration;
  - `BroadcastChannel('p2pchat-codes')` (`app/app.js:1760-1790`).

**Reproduction** (`sw_proofs.mjs`, P4). A page at `/other/` on the same origin runs a few lines
of script:

```
regs:  ["http://127.0.0.1:…/ephem/app/"]            ← it can also unregister it
slots: [{ id: "p2pchat-id-…", label: "work", handle: "anon_5b4405", blobLen: 3 }]   ← key files readable
poisoned: "ephem-d35449100f59"                     ← cache.put('/ephem/app/', <its HTML>)
then /ephem/app/ loads → title "poisoned by /other/ | can read IndexedDB: object",  CSP meta: false
```

**Impact.** Any script running anywhere on `darkcite.github.io` gets persistent code execution in
Ephem. The poisoned entry is served by Ephem's own pinning worker until the next deploy, and the
injected page can re-poison the cache on every load. That script can come from:

- a sibling repo's site with a third-party script;
- an XSS in any sibling page or in this repo's `checks/` pages;
- a merged PR in another repo.

It can also:

- copy every remembered encrypted key file for offline guessing;
- read the plaintext identity handles;
- listen to `p2pchat-codes` to receive forwarded answer and reconnect codes, or post its own
  (`app/app.js:1785-1789` applies any code that `code_fits`);
- frame the app and script it, since the frame is same-origin.

The trust base becomes every Pages site of the account, not "the code served by the static host"
of this app (P9, §5).

**Fix.**

1. Serve Ephem from an origin of its own:
   - a custom domain with a CNAME, or a dedicated GitHub account or organisation whose only Pages
     site is Ephem;
   - publish only `index.html`, `site.css` and `app/` (a Pages workflow or a `gh-pages` branch),
     never `checks/`.
2. Defence in depth in `sw.js`: write the SRI of every precached file into `sw.js` (stamp.py
   already has them), and refuse to serve a cached response whose hash differs. Re-fetch it
   instead. This catches cache poisoning, but not unregistration, so 1 is the fix.
3. Document the origin requirement in §4.1 and §17.

### W-3 (medium): `tor.html` and `channel.html` are not pinned, and a deploy breaks Tor mode

**Evidence.**

- `TOR_FILES` (`app/sw.js:12`, from `tools/stamp.py:28`) are not precached.
- On a cache miss, the fetch handler fetches from the network and stores any `res.ok` response
  for a Tor path in the *current* version's cache, with no check (`app/sw.js:34-36`).
- The wasm and JS modules are safe: the page requests them with `integrity`, and the SW's
  `fetch(req)` keeps it.
- `tor.html` and `channel.html` are navigations: nothing checks them.

**Reproduction** (`sw_proofs.mjs`, P3). With V1 installed and Tor never opened, the host serves a
different `tor.html` (here: another build's app.js hash):

```
p3_tor_title: "tor.html of another build"
p3_cached_in_v1: { cache: ["ephem-d35449100f59"], cachedTitle: "tor.html of another build" }
p3_after_host_reverts: "tor.html of another build"     ← stuck in the V1 cache
console: "Failed to find a valid digest in the 'integrity' attribute for resource …/app.js"
p3_app_started: "starting"                              ← the Tor page never starts
```

**Impact.**

- (a) A hostile or changed `tor.html` bypasses the version pin and stays pinned.
- (b) In the honest case, this breaks Tor mode for users who installed one build and first open
  Tor mode after the next deploy:
  - The new `tor.html` pins the new `app.js`, but the SW serves the old one, and the browser
    refuses it.
  - The Tor page then never runs `registerWorker`, so it never offers the update.
  - Tor mode stays broken until the user accepts the update from the direct page. The page shows
    no error.

**Fix.** Precache `tor.html`, `channel.html` and `redirect.js` (a few KB) in `FILES` at install.
Keep only `pkg/ephem_tor.js` and `pkg/ephem_tor_bg.wasm` lazy (both are integrity-pinned). The
lazy branch should never store `text/html`.

### W-4 (medium): A peer-controlled nickname splits the contacts list and passes the impersonation warning

**Evidence.**

- Peer nicknames are checked for length and UTF-8 only, never for control characters:
  - HELLO parse: `crates/core/src/session.rs:1096`;
  - the stored contact: `Contact::set_nick`, `crates/crypto/src/contacts.rs:96-104`;
  - our own nickname: `Settings::set_nick`, `crates/core/src/session.rs:130-138`.
- `proto::card::valid_nick` (`crates/proto/src/card.rs:32`) does reject control characters, but
  it is used for cards only.
- §7.5 says the contact's nickname is "chosen by the user, not by the peer". The UI saves the
  peer's own HELLO nickname:
  - "Add to contacts": `app/app.js:1149`;
  - accepting a card request: `app/app.js:1875`;
  - `fillContactNick` renames the contact to it automatically: `app/app.js:1860-1865`.
- `App::contacts()` serialises rows as `hex \t flags \t nick \t handle \n`
  (`crates/wasm/src/lib.rs:831`). `contactRows()` splits them on `\n` and `\t`
  (`app/app.js:1286-1288`). `fillContactNick` does the same (`app/app.js:1863`).

**Reproduction** (`nick/src/main.rs`). Mallory's 30-byte HELLO nickname is
`"x\tanon_00\nZ\t3\tAlice\tanon_zz"`:

```
0707…07	1	Alice	anon_21a0a6        ← the real, verified Alice
0909…09	0	x	anon_00                  ← Mallory, now shown with a handle he chose
Z	3	Alice	anon_zz	anon_cfdabe        ← a fake row: flags 3 = "Alice ✔", "Connect through Tor"
impersonated("Alice")=true  ("Alice ✔")=false  ("Аlice" Cyrillic)=false  ("Al​ice")=false
```

**Impact.**

- After one tap ("Add to contacts", or accepting a card dial), the contacts list shows rows the
  user never added, including a "verified ✔" Alice, and a spoofed key-derived handle in the
  person pane (`renderPerson`, `app/app.js:1369`).
- `fillContactNick` can rename *another* nameless contact whose handle Mallory wrote into his
  nickname.
- Even without control characters, a peer calling itself `Alice ✔` (or a homoglyph) looks
  verified in the chat list and contacts. It also passes the impersonation warning, which
  compares ASCII case-insensitively (`contacts.rs:225-230`), so the §7.5 control fails.
- Bounded: connecting to the fake row fails, since its `hex` is not a key. The SAS and the
  person-pane fingerprint stay correct.

**Fix.**

- Use one nickname rule everywhere: `valid_nick`, extended to reject bidi overrides and
  zero-width characters. Apply it in `Settings::set_nick`, `Contact::set_nick` and the HELLO
  parse (a bad HELLO nickname becomes empty, rather than failing the session).
- Return contacts as JSON (or escape `\t`/`\n`).
- Save the contact under a name the user confirms (prefilled with the peer's).
- Draw the ✔ as its own element, never as text after the name, and refuse "✔" inside
  nicknames.
- Compare a skeleton in `impersonated`: NFKC, casefold, confusables map, letters and digits only.

### W-5 (low): Metadata and one key at rest in plaintext

§16 says only the encrypted identity key and non-secret settings are stored. D2 keeps the follow
list in the encrypted key file because "it reveals what you read". F.2.2 says private bridge lines
are semi-secret and are kept in the key file, or in RAM for a temporary identity. The code stores
the following in plaintext:

- **Mirrors** (`app/channels.js`):
  - `localStorage['ephem-mirror-seed-<IPNS name>']` holds the mirror onion's 32-byte private seed,
    keyed by the channel it mirrors (`channels.js:448-456`);
  - mirrored channels are stored under `mirrors/<IPNS name>` in OPFS or IndexedDB
    (`channels.js:461,490`).

  Together these reveal which channels the user follows and mirrors, and let a device thief run
  the mirror's onion.
- **Identity slots:** the plaintext `label` and the key-derived `handle` are stored next to the
  encrypted blob (`app/slots.js:3-5`, `app/app.js:1440`). The handle is what peers see, so a seized
  device links to a chat identity without the passphrase.
- **Tor directory cache:** the IndexedDB key is `dir:<bridge fingerprints>` (`app/app.js:1920`),
  so it also holds the fingerprints of a user's private bridges, for temporary identities too.

**Fix:**

- Derive mirror seeds from the identity (`channel_seeds`-style HKDF) for a saved identity, or keep
  them in a key-file TLV; for a temporary identity keep them in RAM.
- Name stored mirror directories by `BLAKE2s(device secret ‖ name)`.
- Key the directory cache by a hash of the fingerprints.
- Show only the label in the slot list, and the handle after sign-in. Alternatively, document
  these in §16.

### W-6 (low): Clipboard

- `app/app.js:554`: the message "Copy" action writes chat plaintext to the system clipboard and
  never clears it. §16 forbids messages on the clipboard "beyond the moment of sharing", and the
  clipboard can be synced across devices (iCloud and Windows).
- `copyLink` (`app/app.js:1537`) writes `''` 60 s later without checking whether the clipboard
  still holds the code, so it erases whatever the user copied meanwhile.

**Fix:**

- Give message copies the same 60 s clear, or drop the action.
- Before clearing, `readText()` where permitted and clear only if it still equals the code.
  Otherwise accept the overwrite and say so.

### W-7 (low): The reproducible-build claim is not implemented

§17.2 says builds are "reproducible (pinned toolchain, `--remap-path-prefix`)". The repo has:

- no `rust-toolchain.toml`;
- no remap flag in `.cargo/config.toml` or `build.sh`;
- an optional `wasm-opt` of any version (`build.sh:44-46`).

The shipped `app/pkg/ephem_tor_bg.wasm` holds 458 absolute paths `/root/.cargo/registry/src/…`
(the builder's home). On the owner's Mac these would be `/Users/<name>/…`, which leaks a username,
and the output depends on the build machine.

Otherwise the supply chain is clean:

- `wasm-bindgen` is pinned (`=0.2.129`), and `build.sh` checks that the CLI matches.
- `cargo build --locked` is used.
- All 534 lockfile packages come from crates.io; there are no git dependencies.

`checks/` uses `npm install` (`checks/run_all.sh:102`, README) instead of `npm ci`, so dev tools
may drift within caret ranges. This is test-only and not shipped.

**Fix:**

- Add `rust-toolchain.toml` (pinned channel and `wasm32-unknown-unknown`).
- Add `--remap-path-prefix=$HOME/.cargo/registry/src=/cargo --remap-path-prefix=$PWD=/ephem` to
  the wasm rustflags.
- Pin `wasm-opt` (binaryen version check like `wasm-bindgen`), or drop it.
- Use `npm ci`.
- Add a CI job that builds twice and compares hashes.

### W-8 (low): Unbounded gunzip of the directory snapshot

`vendor/tor-dirmgr/src/storage/memory.rs:367` runs `GzDecoder::new(gz).read_to_string(&mut json)`
with no limit. Its input is the IndexedDB snapshot (`app/app.js:2027`). Only a same-origin writer
can plant a gzip bomb (W-2). The result is that the tab aborts (`panic = "abort"`, wasm out of
memory) at every Tor start until site data is cleared.

**Fix:** wrap the decoder in `.take(MAX_SNAPSHOT)` (a few tens of MB, above any real consensus
plus microdescriptors) and fail closed.

### W-9 (low, hardening): CSP scope and framing

- **`script-src 'self'`:** it equals `https://darkcite.github.io`, so any `.js` from any repo of
  the account is an allowed script source. Today no HTML injection sink was found, so this is
  hardening.
  - Fix: use a path source (`https://<host>/ephem/app/`), or rely on the hash-pinned import map
    plus `'strict-dynamic'` with the hash of the bootstrap.
- **Framing:** a `<meta>` CSP cannot set `frame-ancestors`, and Pages sends no `X-Frame-Options`,
  so any site can frame the app for clickjacking (SAS "They match", "Update", "Accept"). Storage
  partitioning limits this to a fresh, empty instance.
  - Fix: add frame-busting in `app.js` (`if (top !== self)` show a link and stop).
- **Trusted Types:** consider `require-trusted-types-for 'script'`. The few `innerHTML`
  assignments are constants or the Rust QR SVG and would need one policy.

### W-10 (info)

- **IP mask:** `renderPath`'s regex (`app/app.js:1109`) does not mask `[fe80::1%en0]`, because the
  zone id `%` is outside `[0-9a-fA-F:.]`. Checked with node. Only the user sees it, and only if
  the browser reports such a candidate. Fix: `/\[[^\]]+\]/`.
- **Passphrase strength:** `saveIdentity` enforces 12 code points (`app/app.js:1609`), while §21
  says the UI "enforces a minimum passphrase strength".
- **Shift+Reload** bypasses the service worker (part of W-1).

## What is solid (tried and could not break)

- **No DOM XSS sink with attacker data.** Every peer or network string goes through
  `textContent`, `value` or `title`. The only `innerHTML` assignments are constant templates
  (`app.js:263,305,991,1240,1302`; `channels.js:257,544,1019`) and the QR SVG, whose builder echoes
  no input. `refreshQuotes` builds its selector from numbers only.
- **Stamped integrity is consistent.** In both pages the import map, `app.js`/`app.css` SRI,
  wasm SHA-384 and CSP `sha256` of the import map all match the shipped files (recomputed).
  - A changed `app.js` is refused (seen in P3's console).
  - The lazy Tor wasm and JS are fetched with integrity (`channels.js:139-141`), and the SW's
    `fetch(req)` carries it, so a wrong body is never cached.
- **CSP:** no inline script, `base-uri 'none'`, `form-action 'none'`, no `unsafe-eval` (only
  `wasm-unsafe-eval`). `channel.html` has its own minimal CSP with SRI on `redirect.js`.
- **Fragments and referrer:** fragments are removed with `replaceState` before any await, and
  `<meta name="referrer" content="no-referrer">` is set. Codes pass only in fragments, never to
  the host.
- **Notifications** never contain message text, and only show while the page is hidden. In-app
  notices show who and how many, never text.
- **Passphrases:** `&mut [u8]` arguments are zeroed in Rust and copied back, so the JS
  `Uint8Array`s end up zeroed too. Input fields are cleared at once.
- **Vendor patches** match `vendor/README.md` exactly; diffed against the crates.io 0.46.0
  tarballs:
  - `arti-client`: `client.rs` (in-memory state manager, `wait_for_stop` gated);
  - `tor-dirmgr`: `Cargo.toml`, `config.rs`, `err.rs`, `lib.rs`, `storage.rs` and the new
    `storage/memory.rs`;
  - `tor-persist`: `lib.rs` and `state_dir_mem.rs`;
  - `tor-hsservice`: `replay.rs` and `ipt_mgr.rs`.

  There are no other changes. The directory snapshot import re-enters arti's normal cache
  validation (consensus signatures against the built-in authorities). Microdescriptors are
  matched by digest; from reading arti this looks right, but it was not tested.
- **`Cargo.lock`:** all 534 packages come from crates.io, there are no git dependencies, and
  `--locked` is used. `wasm-bindgen` is pinned and checked against the CLI.
